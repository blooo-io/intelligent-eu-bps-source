# D5.5 source realignment — arbitrations validated by the Blooo product owner, 2026-11-24

Context: repo `blooo-io/intelligent-eu-bps-source` develop @6a24cc3 (snapshot: outputs/repo). Gap audit and source baseline: `reference-internal/` of the handoff package (do not commit). Deadline: D5.5 V1 30/11/2026; the whole realignment is done in this sprint (≤ 6 days).

## Target model ("two levels", ontology Billing → Invoice → Payment)
- **Level 1 — monthly participant statement** (ontology `Billing` record): one per participant per billing period (monthly default; quarterly allowed). Shows total bought, total sold, net balance, the list of invoices (invoiceIds) and their status. This is the "one invoice object per user per month" of D5.5 scope §7.2. It is NOT a payable document.
- **Level 2 — legal invoices per producer→consumer pair** (ontology `Invoice`): issued in the producer's name (self-billing; mandate accepted by producers in the T&C), addressed to the consumer, netted per pair, one per pair and period. Paid directly to the producer's Stripe Connect account (direct charge). **The platform never holds or routes funds (A1).**
- **Threshold (A3):** per-pair minimum (default 5 EUR / 5 CHF, configurable per community); below it the amount is carried forward; forced at year end or participant exit. **Early settlement is removed** (REQ-057 stays deprecated; remove endpoint, UI, workflow).
- **Payout (A2):** "payout" = Stripe payout from the producer's connected account to their bank. Connected accounts are switched to a **manual payout schedule**. A participant triggers a withdrawal of their available balance; a community setting `autoPayout` (default false) triggers it automatically. A payout of a period's amount is allowed only once the invoices of that period where the participant is the producer are Paid (debtors have paid). Payout status tracked through `payout.*` webhooks (connected account events).
- **KYC (A5):** every participant (consumer, producer, prosumer) gets a Stripe Connect account with Stripe-hosted/embedded onboarding (KYC); community managers do Stripe Identity verification only. `kycVerified` (ontology UserAccount) is set by billing and gates statements, invoices, payments and payouts. Published on EWDS.
- **Invoices PDF (A6):** generated in-house with `pdf-lib` (MIT), stored in the billing DB, legal number sequential per producer (issuer) owned by billing; Stripe Invoicing removed; invoice e-mail sent by billing (notification module).
- **Project UI (A7):** everything goes through the EWDS, no direct link to Blooo. Reads: billing publishes `billingStatement`, `billingInvoice`, `billingPayment`, `billingPayout`, `billingKycStatus` records (`billingKycStatus` = UserAccount: KYC **+ T&C**, INT-448). **Actor admin data:** R2M publishes `actor` create/update (CSV in R2M = N Actor messages); BPS intake only — no billing-service CSV fallback (INT-447). Actions: request/reply on the EWDS (billing command channel): `startPayment`, `requestWithdrawal`, `setInvoiceStatus` (manager, reason mandatory), `startKyc`, `acceptTerms`, `sendReminder`, `triggerBillingRun`, `setupPaymentMethod` (A7-bis). Datamodel + flows: `docs/architecture/06-datamodel-ontology.md`, `07-scenario-flows.md` (INT-449). Where a card/IBAN entry, 3-D Secure, SEPA mandate or KYC is needed, **the project UI chooses per request** (`surface`): `hosted` → the reply carries a Stripe-hosted URL (Checkout Session / Account Link / Identity session); `embedded` → the reply carries a short-lived `clientSecret` + publishable key (+ connected account ref) for Stripe.js / Connect embedded components inside the project UI (A7-bis, 24/11). Never a Blooo URL; sensitive data never transit through billing or the EWDS. `apps/web` stays only as the reference client for adopters without the project UI.
- **Adapters (A8, revised):** real EWDS Client Gateway adapters (trade source, Actor intake, erasure intake, tariffs, command channel, publication) selected by environment variables and **switched on (live EWDS) in every deployed environment**; mock only for local development and automated tests. No bilateral REST to GSY in production (REST off-chain adapter = test fixture only). Missing EWAG roles/topics are alerted and logged, never answered by switching back to mock.
- **Identity (A9):** Keycloak kept as is; no DID/VC work; OIDC relying party stays vendor-neutral.
